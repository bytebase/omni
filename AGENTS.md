# Omni

Omni is the SQL toolchain Bytebase runs on: one hand-written recursive descent parser per database engine, and the catalog, completion, analysis, and review packages built on its AST. Bytebase imports these packages. Omni owns every decision about what an engine accepts and how its DDL behaves; Bytebase owns everything that needs its metadata store or a live connection.

## Read before working

- Before adding an engine or a capability layer (catalog, completion, review), read [docs/engine-capability-guide.md](docs/engine-capability-guide.md) and [docs/PARSER-DEFENSE-MATRIX.md](docs/PARSER-DEFENSE-MATRIX.md). They say how to build a layer; this file says how to change one.
- Before changing `pg/parser` or `redshift/parser`, read [pg/parser/AGENTS.md](pg/parser/AGENTS.md) for the FIRST-set and backtracking rules.
- Before reading anything under `docs/plans`, `docs/specs`, or `docs/scenarios`, read [docs/AGENTS.md](docs/AGENTS.md): those are historical records.
- `AGENTS.md` files are the instruction source of truth; `CLAUDE.md` files import them.

## Repository shape

- Every engine is an independent Go tree under its own top-level directory. `cockroachdb/analysis` is the one analysis tree built on a vendor parser: Bytebase dispatches CockroachDB through the PostgreSQL grammar, but CockroachDB's own DDL (UPSERT, statement sources, regional DDL, zone configuration and IMPORT INTO) has no PostgreSQL node, so the judgment walks CockroachDB's AST and the package links CockroachDB's parser. `cockroachdb/driver` is driver-only: it reads that analysis for statement boundaries and judgment, and links CockroachDB's parser for index definitions and its DISTSQL plan. Engines share only `metadata` (the Bytebase metadata proto), `driver` (the contract between Bytebase and the engine driver packages) and `review` (the SQL Review V2 contract, with `review/walk`, the engine-neutral ledger and statement builder WALK_THROUGH follows a change on, and `review/walk/walktest`, the oracle harness that holds each engine's walk to the engine), and `v1review` (the SQL Review V1 contract Bytebase's advisor calls, which neither imports `review` nor shares a type with it) and `enginetest` (committed engine answers: `compat` checks `<engine>/parser/testdata/compat.tsv`, `grammar` generates its rows from the vendor grammar, `grammar/docs` converts a vendor's docs into one, `simulate` checks `<engine>/catalog/testdata/simulate.tsv`, `span` checks `<engine>/analysis/testdata/span.tsv`, `fuzz` holds each parser's `FuzzParse` to the engine contract, seeded from its `compat.tsv`). An engine never imports another engine's catalog or driver. A driver-only tree whose engine has no grammar of its own uses the grammar tree it is dispatched through: `dynamodb/driver` imports `partiql`, `spanner/driver` imports `googlesql` and `pg`, `bigquery/driver` imports `googlesql`, and `cockroachdb/driver` imports `cockroachdb/analysis` and `pg`, as the design's alias table says.
- Fork engines began as mechanical copies and diverge as explicit dialect deltas: `redshift` from `pg`; `mariadb` and `tidb` from `mysql`; `starrocks` from `doris`. A parser fix in a parent usually applies to its forks. Check, port it in the same PR, and name both in the subject (`fix(pg,redshift): ...`). Forks carry no copies of the parent's planning docs or guides; a fork's file points at the parent's.
- An external differential oracle lives inside the engine it checks, and that engine's tests exec it rather than import it: `mssql/scriptdom` (a .NET ScriptDOM CLI, which a recording runs and tapes replay) and `googlesql/spanner-oracle` (a harness on the Spanner emulator, which a recording runs and tapes replay). The latter keeps its own `go.mod` so its Spanner and gRPC dependencies stay out of the root module; build tags cannot do that, since `go mod tidy` resolves every configuration.
- `<engine>/ast/walk_generated.go` is generated from the engine's `parsenodes.go` by `go run ./cmd/genwalker` in pg, redshift, mysql, mariadb, tidb, oceanbase, mssql, oracle, snowflake, and googlesql; cassandra, doris, and starrocks hand-write their walkers. After changing AST node types, run `go generate ./<engine>/ast/...` and commit the result: CI regenerates all ten and fails on any difference.
- Non-test code has zero dependencies, except an engine's `<engine>/driver` package, which links the engine's client (pgx for `pg/driver` and `cockroachdb/driver`, with cockroach-go and cockroachdb-parser for the latter; go-sql-driver/mysql for `mysql/driver`, `mariadb/driver`, `tidb/driver`, `oceanbase/driver`, `doris/driver`, and `starrocks/driver`; go-mssqldb for `mssql/driver`; trino-go-client for `trino/driver`; go-ora for `oracle/driver`; mongo-go-driver and gomongo for `mongo/driver`; azcosmos (with azcore and azidentity) for `cosmosdb/driver`; the AWS SDK for Go v2 (config, credentials and service/dynamodb) for `dynamodb/driver`; cassandra-gocql-driver for `cassandra/driver`; clickhouse-go/v2 for `clickhouse/driver`; the Cloud Spanner clients (`cloud.google.com/go/spanner`, its admin API, and `google.golang.org/api` for the credential options) for `spanner/driver`; the BigQuery client (`cloud.google.com/go/bigquery`, with `google.golang.org/api` for the credential options) for `bigquery/driver`; go-redis for `redis/driver`, with google/shlex for the command lines it splits; gohive v2 for `hive/driver`; gosnowflake v2 (with youmark/pkcs8 for an encrypted private key) for `snowflake/driver`; the Databricks SDK for Go for `databricks/driver`; nothing but the standard library for `elasticsearch/driver`, whose client is HTTP) to implement the driver contract in `driver/`. `gopkg.in/inf.v0` is there for `cassandra/driver`'s decimal rows too. No other package imports a driver package, so a caller of a parser or catalog links no client. `cockroachdb/analysis` is the one non-driver package that links its engine's parser, for the reason above; it holds no client. testcontainers, testify, go-cmp, and yaml in `go.mod` exist for tests and harnesses only.

## Engine contract

These rules were paid for by rework in the PostgreSQL engine (`docs/engine-capability-guide.md` section 4) and bind every engine:

- Every parse function returns `(node, error)`. Never return nil in place of an error, and never discard one with `_`.
- Every AST node carries `Loc{Start, End}` as byte offsets into the text given to the parser. Start is inclusive; End is exclusive and ends at the node's last token, not at the start of the next one. Unknown is `-1`, never `0`.
- No input panics the parser: empty, binary, or truncated at any byte. A parse failure is a `ParseError` carrying a byte offset.
- No input overflows the stack. A Go stack overflow is fatal and `recover` cannot catch it, so it kills the process that called the parser. Every production that recurses goes through `enterNesting` (`<engine>/parser/depth.go`), which fails past `maxNestingDepth` (10,000) levels with a `ParseError`; each recursion cycle passes through one. Lexers and lookahead scanners loop rather than recurse once per token or per nested group, and a nested re-parse carries the depth it started at.
- A left-deep chain (`1 + 1 + ...`, `UNION ALL`, `JOIN`) is parsed by a loop, so it never reaches `maxNestingDepth`, but every term deepens the tree that consumers then walk recursively. After each statement the parser measures the tree's height with its own stack (`treeTooHigh`) and rejects one deeper than `maxTreeHeight` (100,000) with the same error. The measure reaches every node a consumer recurses into, including nested slices and subquery bodies that `ast.Walk` skips, and walks a subtree that two nodes share only once. A recursive pass inside the parser runs after that check or keeps its own stack. mongo keeps method chains in flat lists and elasticsearch builds no tree, so neither has the check.
- `Parse` is strict. It rejects what the engine rejects and stops at the first error. Recovery, partial trees, and diagnostic lists belong in `ParseBestEffort` where an engine offers one. Do not add tolerance to `Parse`.
- A grammar decision cites the upstream grammar or reference page (`gram.y` line, documentation URL). When the upstream text does not settle what the engine accepts, ask the engine: that is what the oracle tests are for.

## Using the parser

Bytebase's adapters under `backend/plugin/parser/<engine>` and omni's own packages (catalog, completion, analysis, review) call the parser the same way. Deviate only for a reason written beside the call.

| Need | Call |
| --- | --- |
| Statement boundaries of a script, valid SQL or not | `<engine>.Split` or `<engine>/parser.Split`. Lexical, never fails. A segment holding no statement (a lone `;`, a comment) is returned marked empty (`Empty()`; a field in mssql and cassandra) |
| Every statement of a script with text, AST, and positions | `<engine>.Parse(script)`, which returns `[]Statement` (pg, redshift, mssql, oracle, cassandra, cosmosdb, mongo) |
| One statement the caller already isolated | `<engine>.Parse` or `parser.Parse`, then assert exactly one non-empty statement |
| An incomplete fragment, as in completion | Complete it first, by wrapping it in a full statement or patching a placeholder at the caret, then parse. A failure there is expected and falls back to lexer-based extraction |
| Tokens without a tree, as in limit rewriting or caret lookup | `parser.Tokenize` or `parser.NewLexer` |

- Split first, then parse each segment. Every `ParseError` and every `Loc` is then relative to text the caller holds. Whole-script `parser.Parse` is for single statements and for internal helpers that report no positions.
- Parse once and pass the AST. A package that receives an AST (analysis, review, a catalog after `Exec`) does not parse the text again.
- Positions leave the parser as byte offsets. They become line and column only at the boundary that reports to a user, through `review.Index` or `review.Position`: lines 1-based, columns 1-based and counted in code points, which is what Bytebase's `Position` holds. Do not write the byte-to-rune loop again.
- A segment parsed on its own has positions relative to the segment. Parse it in place instead, through a ranged entry such as `oracle/parser.ParseRange(script, seg.ByteStart, seg.ByteEnd)` or a lexer base offset as in doris, so positions come out absolute. Never pad the input with spaces (quadratic on large scripts), and never rewrite `Loc` fields through reflection.
- A parse error is returned, or reported as a finding with its position. The one accepted downgrade is feature extraction from a definition the engine already accepted (a synced function signature, an index definition), and the comment on the call says so.
- `ParseError` has the same shape in every engine: `Message string` and `Position int`, the byte offset into the parsed text, implementing `error` and reachable with `errors.As`. An engine may add fields such as `End`, `Line`, `Column`, `RelatedText`, or `Code`, but does not rename those two. `Parse` returns `error`, not a slice. An engine whose strict parse reports every failure of a multi-statement script (trino, googlesql, doris, starrocks) returns a `ParseErrors` list that unwraps to each `*ParseError`; `parser.AllErrors(err)` and `parser.FirstError(err)` read it. The elasticsearch REST console parser is the one non-SQL grammar and keeps its `SyntaxError{ByteOffset, Message}`.
- Every SQL `Split` returns empty segments rather than dropping them, so segments tile the script in every engine and a caller wanting statements skips them; the `Statement` list from `Parse` holds only statements with an AST.
- DDL enters a catalog only through `catalog.Exec(sql, opts)`. It splits and parses itself and returns one `ExecResult` per statement with its line. A synced schema enters through `LoadMetadata`. Callers do not pre-split for `Exec`.
- `<engine>/review.Review(ctx, sql, opts, targets)` splits and parses once inside, treats a syntax error as a finding at its position, and reports every position through `review.Index`. The contract is in [review/review.go](review/review.go).

### Known deviations

The rules above are the target. These places do not meet them yet; do not copy them into new code.

- On the Bytebase side, `ByteOffsetToRunePosition` exists five times and adapters disagree on keeping empty segments. Not omni's to fix, but the reason `review.Index` stays the single implementation.

## Tests

- Engine dialect and DDL fidelity tests live here, beside the package they cover. Bytebase tests its API and workflow against PostgreSQL only and trusts omni's result, so a behavior Bytebase depends on is pinned by an omni test.
- Test against the engine, not against memory. Parser acceptance, catalog results, and generated DDL are verified against a real engine wherever one can run: a recording of the pinned server, which tapes then replay (`ORACLE_PARSER_REF_DSN` judges a recording of `oracle/parser`'s `compat.tsv` on another server of the pinned release). A service with no image records against a pinned account, and its tapes replay with no credentials: Databricks through `DATABRICKS_DSN`, Redshift through `REDSHIFT_DSN` for `redshift/driver` and `REDSHIFT_COMPAT_DSN` for `redshift/compat`'s judge, and BigQuery through `BIGQUERY_CREDENTIALS`, `BIGQUERY_PROJECT` and `BIGQUERY_DATASET`. Gate a test on an environment variable only when it needs a server CI cannot start.
- CI starts no servers. A package starts each server it needs as a testcontainer on first use, shares it among its tests, and removes it in `TestMain`. Container helpers live inside their engine (`mysql/internal/testcontainer`), never in code shared across engines. Use `container.go` and, when needed, `container_test.go` consistently in these packages. Name the package `testcontainer` and import it without an alias. The current backends and outstanding migrations are recorded in [docs/engine-test-matrix.md](docs/engine-test-matrix.md).
- Share a server where you can. A test takes a database or schema on its package's server. A server of its own is justified by something fixed per server: a different image or version, or an init-time setting such as `lower_case_table_names`. A test on a shared server does not name its database (`test`) or read a schema by a literal: `DATABASE()`, `current_database()`.
- Container tests fail when Docker is missing; they do not skip. CI runs every test on every PR with no `-short` and no nightly. Never check `testing.Short()`, and never park a known gap behind a skip. An oracle probe that fails is fixed or recorded with what it must do instead, as `obRefused` and `obGaps` do in `oceanbase/catalog/oceanbase_oracle_test.go`: each fails an entry that no longer holds.
- A `compat.tsv` holds omni's verdict and the judge's for each statement, and `TestCompatibility` replays it with no server (design: `docs/specs/2026-11-11-engine-compatibility-without-servers-design.md`). A row's `rule` column names the grammar rule, and the mapped engines' `<engine>/testdata/rules.tsv` names the parser file and function a reader should start at for that rule; `enginetest/rules` holds the two together and `TestCompatibility` fails a rule with no row, a row naming a missing file or undeclared function, and a row for a rule no row names. Hand-added `suite:`, `issue:` and `cited:` rows name no grammar rule and get no row. The other engines keep no `rules.tsv` yet: their parsers fold many rules into shared dispatch, so naming one reader per rule would guess. Commit a closed gap with `-update-compat`; fill `?` cells, or rejudge after a pin bump in `<engine>/testdata/pins.tsv`, with `OMNI_RECORD=1`. A change to how a judge reads the server's answers is a pin bump too: raise the judge revision, `pins.tsv`'s fifth column, in a change of its own after the reading lands. Never edit an `expected` cell by hand: CI's `compatcheck` fails it. A grammar whose license keeps it out of the repo (OceanBase's, MariaDB's) is named in `<engine>/testdata/sources.tsv`, and `enginetest.Fetched` downloads it once per machine. A test that reaches its server through `<engine>/internal/testcontainer.Open(t)` replays `testdata/tapes/<Test>.tape` and starts none (every package under `cassandra/`, `clickhouse/`, `cockroachdb/`, `cosmosdb/`, `databricks/`, `doris/`, `dynamodb/`, `elasticsearch/`, `googlesql/`, `hive/`, `mariadb/`, `mongo/`, `mssql/`, `mysql/`, `redshift/`, `starrocks/`, `tidb/`, `oceanbase/`, `oracle/`, `pg/`, `redis/`, `spanner/` and `trino/`, so far); record it with `OMNI_RECORD=1` after changing what it sends, and never edit a tape by hand. An engine whose client is not `database/sql` records through `tape.OpenRaw`, which holds each request and answer as opaque text (`mongo/driver`, `cosmosdb/driver`, `dynamodb/driver`, `cassandra/driver`, `databricks/driver`, `elasticsearch/driver`, `spanner/driver`, `redis/driver` and `bigquery/driver`, so far).
- A document's recording command names a test that exists, and `enginetest`'s `TestDocumentedRecordingCommands` fails one that does not: a `-run` pattern that matches nothing exits 0, records nothing, and reads as a pass in a file whose purpose is to be run later. A row whose test is not written yet says so in prose instead of publishing a pattern.
- A `simulate.tsv` holds, for each DDL statement on a fixture (`<engine>/catalog/testdata/fixtures`), what omni's catalog does and what the engine did: the error code (a SQLSTATE for pg), or `ok:` and a hash of the stored schema (oceanbase/catalog, tidb/catalog, mariadb/catalog, mysql/catalog, pg/catalog, oracle/catalog and mssql/catalog, so far; a subdirectory such as `queries/`, `programs/`, `pg18/` or `mysql84/` holds another suite, with its own test). `TestSimulation` replays it from its tape. `-update-compat` commits the rows a fix moved, to the engine's outcome or to another difference, and never a row that agreed and no longer does. `OMNI_RECORD=1` runs every row again, which a new row or fixture needs.
- A `span.tsv` holds, for each query of a corpus on a fixture, the output columns, lineage and tables read as `ResolveQuerySpan` answers them and as the engine states them (mariadb, mssql, mysql, oceanbase, pg, tidb and trino `analysis`, so far). `TestQuerySpanFidelity` replays it from its tape, and it is updated and recorded as a `simulate.tsv` is.
- Pinned images are part of the recorded expectations: `trinodb/trino:482` in `trino/testdata/pins.tsv` and `trino/internal/testcontainer`, the Spanner emulator `1.5.54` in `googlesql/testdata/pins.tsv`, `googlesql/internal/testcontainer` and `googlesql/spanner-oracle`, and again, as the driver's own row, in `spanner/testdata/pins.tsv` and `spanner/internal/testcontainer`, `mysql:8.0.46` and `mysql:8.4.13` in `mysql/internal/testcontainer`, `postgres:17.12-alpine` and `postgres:18.7-alpine`, and for `pg/driver` one image of each major release from 12, in `pg/testdata/pins.tsv` and `pg/internal/testcontainer`, `gvenzl/oracle-free:23.26.3-slim-faststart` in `oracle/testdata/pins.tsv` and `oracle/internal/testcontainer`, `mcr.microsoft.com/mssql/server:2022-CU27-GDR1-ubuntu-22.04` and `mcr.microsoft.com/dotnet/sdk:8.0.425` (the ScriptDOM harness, role `scriptdom`) in `mssql/testdata/pins.tsv` and `mssql/internal/testcontainer`, `oceanbase/oceanbase-ce:4.3.5.6-106000012026040916` (booted SLIM) in `oceanbase/internal/testcontainer`, `mariadb:11.8.8` in `mariadb/testdata/pins.tsv` and `mariadb/internal/testcontainer`, `dyrnq/doris:3.1.4` in `doris/testdata/pins.tsv` and `doris/internal/testcontainer`, `starrocks/allin1-ubuntu:3.4.10` in `starrocks/testdata/pins.tsv` and `starrocks/internal/testcontainer`, `mongo:8.0.38` in `mongo/testdata/pins.tsv` and `mongo/internal/testcontainer`, `cassandra:5.0.9` (role `driver`; the `default` row beside it is the CQL grammar's, no image) in `cassandra/testdata/pins.tsv` and `cassandra/internal/testcontainer`, `docker.elastic.co/elasticsearch/elasticsearch:8.19.25` in `elasticsearch/testdata/pins.tsv` and `elasticsearch/internal/testcontainer`, the Cosmos DB emulator `2.14.28` as role `emulator` in `cosmosdb/testdata/pins.tsv` and `cosmosdb/internal/testcontainer` (one per machine, on the port it advertises), `amazon/dynamodb-local:3.3.2` in `dynamodb/testdata/pins.tsv` and `dynamodb/internal/testcontainer`, `apache/hive:4.0.1` in `hive/testdata/pins.tsv` and `hive/internal/testcontainer` (with the `hive-site.xml` beside it, which keeps the warehouse on the container's filesystem and lets a table be managed), and `redis:7.4.12-alpine` in `redis/testdata/pins.tsv` and `redis/internal/testcontainer` (started cluster-enabled, one node owning every slot), and `clickhouse/clickhouse-server:26.8.38.9` in `clickhouse/testdata/pins.tsv` and `clickhouse/internal/testcontainer`, and `cockroachdb/cockroach:v25.2.3` in `cockroachdb/testdata/pins.tsv` and `cockroachdb/internal/testcontainer` (one single-node server per top-level test, so every recording starts from the same catalog state). A testcontainer starts the pin as `image@digest` (`Pin.ImageRef`), so a moved tag cannot select another image, and its `checkDigest` still reads what the daemon started; googlesql's harness and mssql's ScriptDOM start their pins by digest without a container check. Upgrading one means rerunning its oracle tests and reading the drift, not editing expectations to match.

- CI runs the sweeps at `SPLITTEST_N=1000000` and `WALK_SWEEP_N=500`; local defaults are smaller. A sweep on tape reads none of them: its size and seed are constants beside the test (`oceanBaseSweepN` in `oceanbase/review`, `s3DiffN` in `pg/splittest`, `walkSweepN` in `pg/review`), changed only with a recording.
- A PR runs what `scripts/affected-packages.sh` derives from the diff: each top-level directory it touches and the ones that import it. `go.mod`, `go.sum`, and `.github/` run everything; `docs/migration/<engine>/` counts as that engine, and the rest of `docs/`, other Markdown, and root files run nothing.

## Verification

During iteration, run the focused test with the regex quoted:

```bash
go test ./pg/parser/ -run '^TestName$' -count=1
```

Before handoff, in order:

1. `gofmt -w` on the Go files you modified. Parts of the tree are not gofmt-clean; format only what you touched.
2. `go build ./...`
3. `go vet ./...` and fix every finding; the tree carries none.
4. `go generate` for any AST package you changed, then confirm `git status --porcelain` is empty apart from your edits.
5. `go test ./<engine>/...` for every engine you touched. To see what CI will run, `scripts/affected-packages.sh origin/main`.
6. For `proto/`: run the buf commands from the proto step of [.github/workflows/ci.yml](.github/workflows/ci.yml), which holds the only buf version pin.
7. For a nested module (`googlesql/spanner-oracle`): `cd` into it and `go test ./...`; `./...` at the root does not reach it.

Correct failures before rerunning. Report an unavailable prerequisite (no Docker, no DSN) explicitly rather than as a pass.

## Documents

- Scenario checklists go in `docs/scenarios/<engine>/`, dated plans in `docs/plans/`, dated designs in `docs/specs/`, per-engine migration notes in `docs/migration/<engine>/`, and prompt templates in `scripts/prompts/`. Nothing of that kind goes in the repo root.
- `SKILL.md`, `PROGRESS*.json`, and `SCENARIOS-*.md` inside engine directories are artifacts of the batch pipelines that built the engine. They are not guidance for changing it.
- Write `<repo root>`, never an absolute path, in prompts and guides.

## Commits and pull requests

- Subject: `<type>(<scope>): <what changed>`, with type one of `fix`, `feat`, `test`, `perf`, `ci`, `docs`, `chore` and scope the engine directory, listing every engine the change touches (`fix(mysql,mariadb,tidb): ...`), or `review`, `catalog`, `ci` for cross-engine work. A Linear key goes in parentheses at the end: `fix(oracle): support constraint_state clause on constraints (BYT-10010)`.
- One PR per change; a parent and its forks are one change.
- Bytebase pins omni by commit in its `go.mod`. A change Bytebase needs is not done until that pin is bumped there and its tests pass.
